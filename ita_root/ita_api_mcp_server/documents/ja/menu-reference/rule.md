# rule reference

OASEのルール。フィルター結果に基づき「どのアクションを実行するか」「どんな結論イベントを生成するか」を決める。**`filter`と`action`を先に作成しておく必要がある**。6メニューの中では最後に作成する。

## filter_a / filter_operator / filter_b columns（相互排他、重要）

- `filter_a`は必須。
- `filter_b`と`filter_operator`は**両方指定する、または両方未指定にする**。片方だけ指定するとエラーになる。
- `filter_a`と`filter_b`に同じフィルターを指定することはできない。
- `filter_operator`に指定できる値は次の3つのみ:
  - `A and B` : フィルターAとBの両方にマッチしたときだけ条件成立
  - `A xor B` : **その判定周期で**フィルターAとBのどちらか一方だけにマッチしたときに条件成立（もう片方を待たない。「XOR相関（A xor B）」節を参照）
  - `A -> B` : フィルターAにマッチした後にフィルターBにマッチしたときに条件成立（時系列相関）。「Bが来なければ」は表せない（「時系列相関（A -> B）」節を参照）
- 単一フィルターだけで判定したい場合は、`filter_a`のみ指定し`filter_b`/`filter_operator`は空にする。
- **一意制約は`filter_a` + `filter_operator` + `filter_b` の組合せ。** つまり**同じフィルター構成のルールは2つ作れない**（`The combination is incorrect.` / 499-00201・MSG-00006）。
  - 既存ルールを別ホスト向けに複製する場合、**ルールだけ増やすことはできず、必ず別のフィルターを用意する必要がある**。`filter_condition_json`に`_exastro_host`条件を足した新しいフィルターを作り、それを`filter_a`に指定すること（`filter.md`参照）。
  - 逆に、`action`の`event_collaboration`を`True`にしてイベント発生元ホストで実行する構成なら、ルールもフィルターも複製する必要はない（1組で全ホストをカバーできる）。

## 1つのイベントで動くルールは1つだけ（重要）

- ルールにマッチしたイベントは**予約済み（判定済み）になり、他のルールの判定には使われない**。1つのイベントが複数のルールの条件を満たしていても、実際に動くのは**優先順位が最上位の1本だけ**である（`rule_priority`節を参照）。
  - フィルターが同じでも異なっていても同様。「同じイベントでルールAとルールBの両方を動かす」ことはできない。
- 1つのルールに指定できる`action_id`は1つだけ。
- したがって「既存ルールにマッチしたら、今のアクションに**加えて**別のConductorも実行したい」という要望は、ルールやフィルターを増やすだけでは実現できない。下記「既存ルールにマッチしたら別のConductorを実行する」節の方法を使うこと。


## AND相関（A and B）— 2つのイベントが「同時に」起きたときだけ動かす

- `filter_operator: "A and B"`は、フィルターAとフィルターBの**両方に、まだ使われていない有効なイベントがある**ときに成立する。
- **「同時に」は「同じ瞬間」ではない。** 先に届いたイベントは、収集設定の`ttl`（既定3600秒）が切れるまで待ち続ける。その間にもう片方が届けば成立する。提案時には「〇秒以内に両方そろえば対処する」という意味であることを、実際の`ttl`の値を添えて説明すること。
- 片方のフィルターは既存のもの（例: CPU高負荷用）を流用してよい。もう片方（例: メモリ高負荷用）のラベル付与とフィルターが無ければ作る。

### 既存の単独ルールとフィルターを共有するとき（最重要）

例えば既存の「CPU高負荷だけで動くルール」がある状態で、同じCPU用フィルターを`filter_a`に使ったAND相関ルール（CPU and メモリ）を追加すると、**優先順位によって次のどちらかになる**（製品の判定エンジンで確認した挙動）。

| 優先順位 | CPUとメモリが`ttl`内にそろった | CPUだけが来た |
|---|---|---|
| AND相関が上位（同じ優先順位の場合も、`filter_b`のあるAND相関側が先に評価される） | AND相関が動く | 単独ルールは**すぐには動かない**。CPUのイベントが`ttl`切れでタイムアウトした時点で、初めて単独ルールが動く（対処が最大`ttl`秒遅れる） |
| 単独ルールが上位 | 単独ルールがCPUのイベントを使ってしまい、**AND相関は動かない** | 単独ルールがすぐ動く |

- つまり「既存の単独ルールを残したまま、AND相関も期待どおりに動かす」ことはできない。「〇〇と△△が同時に起きたときだけ対応したい」という依頼では、**既存の単独ルールの扱いを必ずユーザーに確認すること**。選択肢は次のとおり。
    1. **既存ルールをAND相関に変える**（`Update`で`filter_b`と`filter_operator`を追加。`rule_label_name`等は変えずに全列を再送）。「だけ」の要件どおりで副作用が無い。**第一候補**
    2. 既存ルールを無効化（`available_flag: False`）または廃止し、AND相関ルールを新規作成する
    3. 既存ルールを残す。この場合は上の表の副作用（AND相関を上位にするとCPU単独の対処が最大`ttl`秒遅れる／単独を上位にするとAND相関は動かない）を**具体的な秒数とともに**説明し、了承を得ること
- 優先順位を同じ値のままにしない。同じ優先順位だとフィルターIDの並びで評価順が決まり、意図が読めなくなる。


## XOR相関（A xor B）— 「どちらか一方だけ」の依頼を受けたとき（重要）

**XORは「片方だけ起きたら対応し、両方起きたら対応しない」ではない。** 製品の判定エンジンで確認した挙動は次のとおり（AND相関とは違い、もう片方を待たない）。

| イベントの来方 | XORルール単体の結果 |
|---|---|
| 片方だけ来た | **その判定周期のうちにすぐ成立**する（`ttl`内にもう片方が来ないかは待たない） |
| 同じ判定周期に両方来た | 両方のイベントが**未知**になり、何も動かない（他のルールにも渡らない） |
| 片方が来て、少し後（`ttl`内）にもう片方が来た | **XORが2回成立**し、両方に対応してしまう |

- つまりXORは「それぞれが単独で来たら毎回動き、同じ周期にそろったときだけ何もしない」。**「`ttl`秒以内に両方そろったら対応しない」と説明してはいけない**（AND相関の「`ttl`まで待つ」挙動はXORには当てはまらない）。
- 「〇〇または△△のどちらか一方だけ起きたら対応したい」と言われたら、**どちらの意味かをユーザーに確認すること**。
    1. 「それぞれ起きたらすぐ対応したい。ほぼ同時に起きたときだけ省ければよい」→ XORで足りる
    2. 「一定時間内に両方起きたら対応しない。片方だけのときだけ対応したい」→ XORでは実現できない。下の「吸収ルール」構成を案内する
    3. 「どちらが起きても対応したい（両方なら両方）」→ 単独ルールを2本作る（OR相当）

### 「一方だけ」を厳密に実現する構成（吸収ルール）

アクションを付けないAND相関ルールを上位に置き、単独ルールを下位に置く。判定エンジンで確認した挙動:

| ルール | 優先順位 | 内容 |
|---|---|---|
| 吸収用のAND相関ルール | 上位（例: 1） | `filter_a`=〇〇、`filter_b`=△△、`A and B`、**`action_id`なし** |
| 〇〇の単独ルール | 下位（例: 2） | `filter_a`=〇〇、対処のアクション |
| △△の単独ルール | 下位（例: 2） | `filter_a`=△△、対処のアクション |

- `ttl`以内に両方そろう → 吸収ルールがそろったイベントを使い、何もしない
- 片方だけ → もう片方を`ttl`まで待ち、来なければタイムアウト時に単独ルールが動く。**対処は`ttl`秒遅れる**
- この遅れ（今の収集設定の`ttl`の秒数）を必ずユーザーに伝えて了承を得ること。

### 既存の単独ルールとフィルターを共有するとき

| 優先順位 | 〇〇だけ来た | △△だけ来た | 同じ周期に両方 |
|---|---|---|---|
| XORが上位 | XORが動く。**既存の単独ルールは一度も動かない** | XORが動く | 両方未知。既存ルールも動かない |
| 既存の単独ルールが上位 | 単独ルールが動く | **何も動かない**（XORルールは事実上一度も動かない） | — |

- 既存の単独ルールを残したままXORを足すと、どちらを上位にしても期待どおりにならない。既存ルールの扱い（XORに変える／無効化する／吸収構成に組み替える）を必ず確認すること。**AND相関の表（「最大`ttl`秒遅れる」）をXORに当てはめてはいけない。**


## 時系列相関（A -> B）と「〇分たっても□□が来なければ」（重要）

- `filter_operator: "A -> B"`は、**フィルターAのイベントの後に**フィルターBのイベントが来たときに成立する（判定エンジンで確認）。
    - A → Bの順（`ttl`内） → 成立
    - Aだけ → 何も起きない（Aは`ttl`切れでタイムアウトする）
    - B → Aの順（逆順） → 成立しない
- つまり`A -> B`は「**復旧通知が来たら**」を表すもので、「**来なければ**」は直接は書けない。

### 「〇〇が発生してから△△分たっても□□（復旧通知）が来なければエスカレーション」の作り方

アクション無しの`A -> B`ルールを上位、Aだけのエスカレーションルールを下位に置く（判定エンジンで確認）。

| ルール | 優先順位 | 内容 |
|---|---|---|
| 吸収ルール | 上位（例: 1） | `filter_a`=〇〇（障害）、`filter_b`=□□（復旧）、`A -> B`、**`action_id`なし** |
| エスカレーションルール | 下位（例: 2） | `filter_a`=〇〇（障害）だけ、エスカレーションのアクション |

| イベントの来方 | 結果 |
|---|---|
| 障害のあと`ttl`内に復旧 | 吸収ルールが成立し、エスカレーションしない |
| 障害だけ（復旧が来ない） | 障害のイベントが`ttl`切れでタイムアウトした時点で、エスカレーションルールが動く |
| 障害のあと`ttl`切れより後に復旧 | `ttl`切れの時点でエスカレーションする（遅れた復旧は吸収されない） |
| 復旧が先に残っていて、その後に障害 | 吸収されない。障害の`ttl`切れの時点で、先の復旧が**期限切れになっていれば**エスカレーションする。**まだ有効なら、エスカレーションルールにも渡らず、障害はそのままタイムアウトする（何も起きない）** |

- 障害と復旧が同じ収集設定から来る（同じ`ttl`）なら、先の復旧は必ず障害より先に期限切れになるので、上の表の最後の行はエスカレーションになる。**障害と復旧で有効期限が違う場合（例: 障害の側が結論イベントでルールの`ttl`が短い）は、先の復旧が残っていると黙ってエスカレーションされない**（判定エンジンで確認）。この場合は`oase_scenario_building.md`の「障害を自動復旧し、直らなければ通知する」節の構成にすること。
- **（障害と復旧が同じ収集設定から来る場合）吸収ルールに`A and B`を使ってはいけない。** ANDは順番を見ないため、前の障害の復旧通知が未使用のまま`ttl`内に残っていると、新しい障害が来た瞬間に吸収され、**エスカレーションされない**（判定エンジンで確認）。必ず`A -> B`（`filter_a`が障害、`filter_b`が復旧）にすること。
- **待ち時間の「△△分」はルールでは設定できない。** イベントの有効期限は**収集設定（`event_collection`）の`ttl`**で決まり、障害のイベントはその秒数でタイムアウトする。ルールの`ttl`列は結論イベントの有効期限で、待ち時間には関係しない。
    - 依頼の「△△分」と収集設定の`ttl`が違う場合は、そのことを必ず伝え、次のどちらにするか確認する。
        1. 収集設定の`ttl`を△△分（秒に換算）に変える。**その収集設定から来るすべてのイベントの有効期限が変わり、AND相関・XORの待ち時間や、他のルールのタイムアウトの時期にも影響する**ので、影響するルールを`menu-filter`で調べて提示すること
        2. 今の`ttl`のまま（待ち時間は`ttl`秒になる）にする
    - 同じ監視ツールに対して収集設定をもう1つ作って`ttl`を変える案は、**同じイベントを二重に取り込む**おそれがあるため、第一候補にしないこと（取得条件で対象を分けられる場合だけ）。
- **エスカレーションルールのフィルター（障害だけ）を、既に単独で使っている既存ルールがある場合**、同じフィルター構成のルールは一意制約で2本目を作れない。既存ルールの扱いをユーザーに確認すること。
- エスカレーションを通知で行う場合は、ルールの事前・事後通知（通知先・通知テンプレート）の設定が必要。通知先が未設定なら、先にその設定が要ることを伝えること。

## action_id column

- 事前に`action`メニューで作成済みのアクション名を指定する。省略可（アクションを実行せず結論イベント生成のみ行うルールも作れる）。

## 既存ルールにマッチしたら別のConductorを実行する（差し替え／追加）

「〇〇ルールにマッチしたら△△（Conductor）を実行して」という依頼には2通りの意味があり、**どちらなのかを必ずユーザーに確認すること**。既にアクションが設定されているルールで、黙って`action_id`を差し替えてはいけない。

| | やりたいこと | 方法 | 触るメニュー |
|---|---|---|---|
| 差し替え | 今のアクションの**代わりに**△△を実行する | △△用の`action`を用意し、既存ルールの`action_id`を`Update`で差し替える | `action`（新規 or 既存流用）、`rule`（更新） |
| 追加 | 今のアクションの**後に続けて**△△も実行する | 結論イベントを使ってルールを連鎖させる（下記） | `label_creation`、`rule`（既存を更新＋新規）、`filter`（新規）、`action` |

- △△の`conductor_class_id`を使うアクションが既にあれば、新規作成せずにそれを流用する（`menu-filter`の`menu: "action"`で確認）。
- 差し替えの`Update`は下記「既存ルールを`Update`するときの注意」節の例のとおり、変更しない列も全て再送すること。

### 追加: 結論イベントでルールを連鎖させる

アクション付きのルールは、**Conductorが正常終了したときに結論イベント**（`_exastro_type`が`conclusion`のイベント）を生成する。この結論イベントを別のフィルターで拾い、2本目のルールで△△を実行する。

```
監視イベント ─▶ 既存ルール（今のアクションを実行。変更なし）
                   │ Conductorが正常終了
                   ▼
               結論イベント（conclusion_label_settings で chain_xxx=true を付ける）
                   │
                   ▼
               新フィルター [["_exastro_type","==","conclusion"],["chain_xxx","==","true"]]
                   │
                   ▼
               新ルール ─▶ △△用のアクション
```

1. `label_creation`で連鎖用のラベルキーを作る（例: `file_copy_trigger`）。
2. 既存ルールを`Update`し、`conclusion_label_settings`に`[["file_copy_trigger", "true"]]`を設定する（変更しない列は全て再送）。
3. `filter`を新規作成する。`filter_condition_json`は`[["_exastro_type", "==", "conclusion"], ["file_copy_trigger", "==", "true"]]`。
4. △△用の`action`を用意する（既存があれば流用）。
5. `rule`を新規作成し、手順3のフィルターと手順4のアクションを紐付ける。

注意点:

- **△△が動くのは、1本目のConductorが正常終了したときだけ。** 1本目が異常終了すると結論イベントが作られないため、△△は実行されない。また実行は同時ではなく**直列**（1本目の完了後）になる。この挙動を提案時に必ずユーザーへ説明すること。
- 結論イベントには`_exastro_rule_name`（元ルールの`rule_label_name`）も自動で付くが、**`_exastro_rule_name`はフィルター条件に使えない**（`filter_condition_json.label_name`のプルダウンに無い）。連鎖させるには上記のように独自のラベルキーを`conclusion_label_settings`で付与する必要がある。
- 既存のフィルターに`["_exastro_type", "≠", "conclusion"]`が入っていることを確認すること。これが無いと、結論イベントが既存ルール自身に再びマッチしうる。

## 多段判定（一次ルールの結論イベントを使って二次判定する）（重要）

「◇◇（ルール名）の判定結果を使って、さらに☆☆という条件で二次判定したい」は、一次ルールの結論イベントを二次ルールのフィルターで拾って作る（連鎖の仕組みは「追加: 結論イベントでルールを連鎖させる」節と同じ）。

### 二次判定に使うラベルを結論イベントに載せる

結論イベントに付くラベルは次で決まる（`ita_by_oase_conclusion/libs/action.py`で確認）。
- `conclusion_label_settings`で指定したラベル（値には**Jinja2が使える**。`A`がフィルターAのイベントのラベル、`B`がフィルターBのイベントのラベル）
- `event_label_inheritance_flag`が`True`のときは、さらに元イベントのラベル（`_exastro_`で始まるシステムラベルの一部を除く。`_exastro_host`やユーザーが付けたラベルは引き継がれる）が**丸ごと**乗る

二次判定に`severity`を使いたいなら、次のどちらかにする。**必要なラベルだけを渡す1の方が、影響範囲が小さく安全**。
1. 一次ルールの`conclusion_label_settings`に`["severity", "{{ A.severity }}"]`を足す（既存の連鎖用ラベルは残す）
2. 一次ルールの`event_label_inheritance_flag`を`True`にする（元イベントのラベルがすべて結論イベントに乗るので、既存の結論イベント用フィルターに意図せずマッチしないか確認が必要）

### 既存の結論イベント用ルールとの関係

- 1つの結論イベントを使えるのも1ルールだけ。一次ルールの結論イベントを既に別のルール（例: 連鎖のファイルコピー）が使っている場合、二次判定のルールとどちらが動くかを決める必要がある（二次判定を優先する／既存側に条件を足す／既存側の結論イベントでさらに連鎖させる）。ユーザーに確認すること。
- 二次判定は、一次ルールのConductorが**正常終了したとき**だけ、**順番に**動く（アクションの無い一次ルールなら、結論イベントはすぐに作られる）。

### 無限ループを防ぐ（必須の確認）

結論イベントが、それを作ったルール自身（または連鎖の前の段のルール）のフィルターを**また満たす**と、ルール → 結論イベント → 同じルール…と動き続ける。判定エンジンでは、二次ルールの結論イベントが二次ルール自身の条件を満たす構成にすると**1回の判定処理が終わらなくなった**（ループ回数の上限`EVALUATE_LATENT_INFINITE_LOOP_LIMIT`はあるが、頼ってはいけない）。提案前に必ず次を確認し、確認した結果を提案に書くこと。
- 各段のルールが作る結論イベントのラベル（継承分も含む）を書き出し、**どの結論イベント用フィルター（`_exastro_type == conclusion`を含むフィルター）にマッチするか**を1つずつ照合する。自分自身や前の段のフィルターにマッチするものがあってはいけない
- 段ごとに**異なる目印のラベル**（例: 一次は`stage=1`、二次は`stage=2`）を結論ラベルで付け、各段のフィルターは自分の前の段の目印だけを条件にする
- 二次ルール（最後の段）では`event_label_inheritance_flag`を`True`にしない。前の段の目印や判定条件のラベルが引き継がれ、自分自身に再びマッチする原因になる
- 監視イベント用のフィルターには`["_exastro_type", "≠", "conclusion"]`を入れ、結論イベントを拾わないようにする

## before_notification_destination / after_notification_destination columns

- 通知先（複数選択）を指定する場合、**対応する通知テンプレート（`before_notification`/`after_notification`、ファイルアップロード項目）と`action_id`を必ずセットで指定する**こと。通知先だけ指定してテンプレートやaction_idが無いとエラーになる。
- 通知テンプレートファイルには`[TITLE]`と`[BODY]`の両方のセクションが必要（Jinja2構文も使用可）。

## ルールの通知（事前通知・事後通知）を設定する（重要）

### 通知先（宛先）はExastro Platformで登録する

- `before_notification_destination`/`after_notification_destination`の選択肢は、**Exastro Platformのワークスペースに登録された通知先**。ITAのメニューではないため、**MCPのツールからは登録できない**。
    - 登録場所: Exastro Platformのメニュー「**通知管理**」→ 通知先ワークスペース一覧 → 対象ワークスペース →「新規通知先設定」
    - メールで送る場合は、さらに「**オーガナイゼーション設定**」→「**メール送信サーバー設定**」が必要（未設定だとメールは送られない）
- `list-menu-info-pulldown`（`menu: "rule"`）で`before_notification_destination`の候補が空なら、通知先は1件も登録されていない。ユーザーに上記の登録を依頼し、**登録した通知先の名前**を教えてもらうこと。メールアドレスをそのまま`before_notification_destination`に入れることはできない。
- 通知先が未登録でも、**テンプレート（`before_notification`/`after_notification`）だけ先に登録することはできる**（通知先が空なら通知は送られない）。通知先を指定するときは、テンプレートと`action_id`が必須。
- テンプレートはファイルアップロード項目なので、文面を`create-text-file`で作って`file_id`を発行し、`maintenance-all`の`fileid`で渡す。ルールの`Update`なので、変更しない列も全て再送すること。

### テンプレートに渡るデータ（共通テンプレートとは形が違う）

ルールの事前通知・事後通知のテンプレートには、次のデータがまとめて渡る（`ita_by_oase_conclusion/libs/notification_data.py`で確認）。**最上位に`labels`は無い**ので、共通テンプレート（`notification_template_common`）の変数（`{{ labels._exastro_host }}`等）をそのまま使うと空欄になる。

| 変数 | 内容 |
|---|---|
| `events` | ルールが使ったイベントの**リスト**。各要素の`labels`にラベル（`_exastro_host`、ユーザーが付けたラベル、`_exastro_fetched_time`（日時に変換済み）、`_exastro_event_collection_settings_name`等）、`_exastro_events`に元のイベントJSON |
| `rule` | `rule_name`、`filter_a_name`、`filter_b_name`、`filter_operator` など |
| `action` | 事前: `action_name`、`conductor_name`、`operation_name`、`host_id` など／事後: `operation_name`、`status` など |
| `action_log` | 評価結果（`rule_name`、`status`、`time_register` など） |
| `conductor` | 事後通知のみ。`status`、`time_start`、`time_end` など |

```
[TITLE]
【運用チーム】CPU高負荷を検知しました（{{ events[0].labels._exastro_host }}）
[BODY]
ルール: {{ rule.rule_name }}
実行する対処: {{ action.action_name }}（Conductor: {{ action.conductor_name }}）
{% for event in events %}
・ホスト: {{ event.labels._exastro_host }} ／ 種別: {{ event.labels.alert_type }} ／ 検知時刻: {{ event.labels._exastro_fetched_time }}
{% endfor %}
```

### 「〇〇のときだけ△△にも通知したい」と言われたとき（条件付きで宛先を足す）

- 通知先はルールごとに決まり、テンプレートの中で宛先を切り替えることはできない。条件（例: `severity == Critical`）を足した**専用のフィルターとルール**を作り、専用ルールを既存ルールより上位にする（既存ルールは優先順位を下げる）。
- 専用ルールにマッチしたイベントは、**既存ルールでは処理されない**（1つのイベントで動くルールは1つだけ）。そのため専用ルールには、既存ルールと同じものを全部持たせること。
    - **通知先は「既存ルールの通知先 ＋ △△」にする。** △△だけにすると、その条件のときに**元の宛先（例: 運用チーム）へ通知が届かなくなる**。依頼が「△△**にも**」なら両方、「△△**だけに**」なら△△のみ。既存ルールに通知先がまだ無い場合も、元の宛先を後で設定するときは専用ルールにも入れる必要があることを伝える
    - アクション（`action_id`）、通知テンプレート、`conclusion_label_settings`（連鎖用ラベル）も既存ルールと同じにする。どれかが欠けると、その条件のときだけ対処や連鎖が止まる
- 既存ルールを`Update`して優先順位を下げるときは、変更しない列も全て再送すること。

### 「イベント種別ごとに通知を変えたい」と言われたとき

- アラートの種類（例: CPU高負荷）ごとに文面や宛先を変えたい → **そのアラートを扱うルール**の事前・事後通知を設定する。どのルールに付けるか（同じアラートを複数のルールが扱っている場合）と、事前・事後のどちらにするかを確認する。
- 共通テンプレート（`notification_template_common`）の`event_type`は、**OASEの通知の種類**（新規受信・新規・既知（判定済み）・既知（時間切れ）・未知 など）であって、アラートの種類ではない。共通テンプレートを書き換えると**すべてのアラート**の通知に影響するので、アラートの種類ごとに変えたい依頼で第一候補にしてはいけない。

## conclusion_label_settings column

- REST入力値は `[[label_key, label_value], ...]` という**2要素配列のリストをJSON文字列化**したもの。マッチ時に生成する結論イベントへ付与するラベルを定義する。
- **登録時に必須**なので、キーは必ず渡すこと。省略すると`{"conclusion_label_settings": ["Required fields."]}`（499-00201）で失敗する。
- **`label_value`を空にしてはいけない。** `[["_exastro_host", ""]]`は`{"conclusion_label_settings": ["Value is required."]}`（499-01707）で拒否される。画面ではその行が値空のデフォルトとして表示されるが、APIは受け付けない。
- 結論ラベルが不要な場合は、空リストを文字列として渡す。
  ```json
  "conclusion_label_settings": "[]"
  ```
- `label_key`は`label_creation`に登録済みのラベルキー（または`_exastro_host`等の予約キー）であること。有効なキーは`list-menu-info-pulldown`で確認できる。未知のキーは`MSG-00032`で失敗する。
- 例: 結論イベントに`severity=high`を付与したい場合
  ```json
  "conclusion_label_settings": "[[\"severity\", \"high\"]]"
  ```

## rule_label_name column

- 結論イベントの`_exastro_rule_name`ラベルに設定される名前。
- **登録後は変更できない**。更新時に別の値へ変えようとするとエラーになる。

## rule_priority column

- 整数、最小値1。**数値が小さいほど優先順位が高い**（`1`が最上位）。画面の項目説明も「数値が小さいものを優先します」。
- 1つのイベントが複数のルールの条件を満たした場合、優先順位が最上位のルールだけが動き、イベントはそこで使われる（他のルールには渡らない）。
- **同じフィルターを複数のルールで使っている場合、そのフィルターのイベントはまず優先順位が最上位のルールだけで判定される。** 最上位のルールが成立しない間（例: AND相関でもう片方のイベントを待っている間）、下位のルールはそのイベントを使えず、**イベントがタイムアウトした時点で初めて**下位のルールの判定に回る。詳しくは「AND相関（A and B）」節を参照。

## ttl column

- 単位は秒。最小値10、最大値2147483647。デフォルト3600。

## 既存ルールを`Update`するときの注意（重要）

- `maintenance-all`の`Update`では、**バリデーションは「今回渡した値」だけで判定される**。既存レコードに入っている値は補完されない。
- そのため`action_id`だけを差し替えるつもりで1項目だけ渡すと、`filter_a`/`filter_b`が未指定として扱われ、次のエラーになる。
  ```
  {"0": {"Individual check": ["Duplicate filters are selected."]}}  (499-00201)
  ```
- **更新前に`menu-filter`で既存レコードを取得し、変更しない項目（`rule_name`/`rule_label_name`/`rule_priority`/`filter_a`/`conclusion_label_settings`/`action_label_inheritance_flag`/`event_label_inheritance_flag`/`ttl`/`available_flag`）も含めてすべて渡すこと。**
- `last_update_date_time`も直前の`menu-filter`で取得した値をそのまま渡す（更新ごとに値が変わるため、連続更新する場合は毎回取り直す）。
- 例: アクションの差し替えのみを行う`Update`
  ```json
  {
    "menu": "rule",
    "records": [{
      "type": "Update",
      "parameter": {
        "rule_id": "<既存のrule_id>",
        "last_update_date_time": "<menu-filterで取得した値をそのまま>",
        "available_flag": "True",
        "rule_name": "<既存と同じ>",
        "rule_label_name": "<既存と同じ>",
        "rule_priority": "1",
        "filter_a": "<既存と同じフィルター名>",
        "action_id": "<新しいアクション名>",
        "conclusion_label_settings": "[]",
        "action_label_inheritance_flag": "True",
        "event_label_inheritance_flag": "False",
        "ttl": "3600"
      }
    }]
  }
  ```
