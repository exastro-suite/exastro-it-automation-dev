## Label Creation

### About Labels
There are two types of labels: "system labels," which are automatically assigned by Exastro, and "user labels," which are configured by the user.
System labels include the event type (_exastro_type) and the evaluated flag (_exastro_evaluated), and are used to manage the state of events.
- Label key
     - Description
- _exastro_event_collection_settings_id
     - The ID indicating which event collection setting was used to collect the event
- _exastro_fetched_time
     - The date and time the event was retrieved
- _exastro_end_time
     - The expiration date and time of the event (TTL)
- _exastro_agent_name
     - The name of the agent that collected the event
- _exastro_agent_version
     - The version of the agent that collected the event
- _exastro_type
     - The event type (regular event/conclusion event)
- _exastro_checked
     - A flag indicating whether a new event notification has been sent (0: not sent, 1: sent)
- _exastro_evaluated
     - A flag indicating whether the event has been rule-evaluated (0: not evaluated, 1: evaluated)
- _exastro_undetected
     - A flag indicating whether the event is unknown (0: normal, 1: unknown)
- _exastro_timeout
     - A flag indicating whether the event has expired (0: valid, 1: expired)

## Deduplication

### About Deduplication
This feature is designed for cases where the event collection system or the OASE agent is made redundant. Even when multiple pieces of event information that are essentially identical are obtained, only the first event is imported, preventing duplicate processing.
When deduplication is enabled in the event collection settings, events with matching values for the label key specified for deduplication are treated as duplicates.
By configuring the deduplication feature appropriately, you can reduce the number of events and hold down system resource consumption.

## Rule Details

### About Rules
A rule is a setting that determines, based on the filter results, "which action to execute" and "what conclusion event to generate."
In a rule setting, Filter A, Filter B, and a filter operator are combined to define the rule match condition.
When an event matches a rule, the configured action is executed, and a conclusion event is generated based on the conclusion label settings.
Executing an action is optional and can be configured in combination as needed.
A priority can be set for a rule, and if multiple rules match, the one with the higher priority is matched.

## Points to Check When a Large Number of Records Appear in Event History or Evaluation Results
If a conclusion event configured in a certain rule is set up in such a way that it matches a filter that leads back to the aforementioned rule,
an infinite loop state occurs, causing a large number of records to continue being registered in Event History and Evaluation Results.
As needed, review your settings, for example by disabling the filter or rule.
